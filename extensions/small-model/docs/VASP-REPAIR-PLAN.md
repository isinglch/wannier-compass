# VASP 接口问题：证据与修复顺序

本轮只读取既有失败产物、本机 VASP/Wannier90 源码及二进制符号，没有重新执行 VASP，
没有改动共享软件。以下把已确认事实与待验证假设分开；修复实施后仍须真实计算验收。

更新：`0.2.0.dev4` 按用户决定取消 cache 与接口总带数必须相等的检查，后续统一使用实际
接口带数。第 1 节的处理方案已据此替换；历史失败证据保留。第 2、3 节段错误与半成品
矩阵的修复尚未实施，本次变化不代表它们已解决。

## 1. 并行布局导致 NBANDS 改变

已确认 soc-0010 的输入为 NBANDS=56，32 MPI ranks、NCORE=1、KPAR=1；stdout 明确
记录实际改为 64。EIGENVAL 为 [144,64]，配置期望为 [144,56]，实际 k 点集合匹配。
这不是 k 网格错误，也没有证据要求模型更换窗口。

VASP 官方说明了并行运行会调整带数，以及 NCORE/KPAR 与带组的关系：
[NBANDS](https://vasp.at/wiki/index.php/NBANDS)、[NCORE](https://vasp.at/wiki/NCORE)。

当前处理：不再以源 cache 带数核验接口带数，也不要求调整并行布局来保持带数不变。
实际 EIGENVAL 总带数减去已批准排除带数得到 `nb`，用于核验 `.win`、EIG、AMN、MMN，
并传给 `disentanglement_state`。源总带数、实际总带数及实际保留带数均写入事实记录。
批准的目标仍在源 cache 上比较，不自动把新增接口态纳入目标，也不选择新的排除列表。

k 点匹配、实际窗口态数约束和矩阵来源/完整性检查保留。带数增加不代表可以使用部分
矩阵或容忍 `.win` 与矩阵不一致。RhSi 的 128 带本来与 32 ranks 兼容仍崩溃，说明
放宽带数检查不能替代下面的崩溃修复。

## 2. 崩溃路径与排除带后的维度：强假设，尚未真实复现验证

对实际 vasp_ncl 可执行文件做符号定位：

| 栈地址 | 符号 |
|---|---|
| 0x1eacdbd | for_deallocate_handle |
| 0x1e994bd | for_realloc_lhs |
| 0x14dc36a | mlwf_mp_mlwf_trafo_run_ |
| 0x14bb355 | mlwf_mp_mlwf_main_ |

本机可读的 `vasp.6.3.0/src/mlwf.F` 显示，`LWANNIER90_RUN=.FALSE.` 时，在已知投影
模式下并不只写矩阵；MLWF_MAIN 还会调用 MLWF_TRAFO_RUN 的 one-shot SVD 路径。
CALC_WANNIER_TRAFO_PROJ 按总 NB_TOT 设置 T/SVD 尺寸，而 A_matrix 的带维是
NB_TOT-NEXCLB。对带排除输入，赋值引起的数组重分配以及后续仍按总带数处理的路径
需要重点验证。源码与二进制的精确构建对应关系也要核对，符号定位没有提供源码行号，
所以现在不能宣称某行代码已被证实为根因。

在实际输入/产物中：

- soc-0018：实际总带数 128，排除 1–20；AMN/MMN 的保留带数为 108。
- soc-0023：实际总带数 128，排除 1–24；AMN/MMN 的保留带数为 104。
- 两例 INCAR 和 OUTCAR 都明确包含 LWANNIER90_RUN=.FALSE.；都在相关阶段段错误。

先做不经过 LLM 的最小接口复现，冻结原科学参数与来源；只改变技术路径，并把每次
改变、资源、完整日志和结果记录清楚。优先检验“排除带后的 one-shot/SVD 维度路径”
这个假设；避免同时修改窗口、投影、k 网格和软件版本而失去诊断意义。

优先考虑的适配器修复路线是：**VASP 生成完整 Bloch 带的原始矩阵；程序严格按已批准
的排除列表提取/重编号矩阵；独立 Wannier90 使用最终科学方案运行。** 这里改变的是
排除操作的落地位置，科学排除列表、目标、投影与窗口都不由程序重新选择。

这一方案必须先验证 VASP 在无内部排除的矩阵生成阶段能正常结束，且不会误用内部
one-shot 产物。然后验证 AMN 的带行、MMN 的两个带轴、EIG 的行号，以及外部 .win
均使用同一份有来源哈希的映射；不能在外部再次重复应用排除。设置最终 num_bands
是已批准列表的机械结果，不是启发式选择。所有下游产品仍检查完整性和来源。

若该方案不足以避免崩溃，下一步才是使用已验证兼容的构建，或在项目专用的软件副本
中启用边界检查/调试符号定位并修补。共享 VASP 安装不直接覆盖；换二进制后仍需固定
科学输入重跑对照。不能假设某个更高版本必然解决。

VASP 会自动填写 num_bands 等接口字段，见官方
[WANNIER90_WIN](https://vasp.at/wiki/index.php/WANNIER90_WIN)；因此不能假定在
WANNIER90_WIN 中写一个值就能约束执行器最终产物。

## 3. 不能复用当前半成品 AMN

本机写出代码以 k、Wannier、band 次序写 AMN，固定每条数据 52 字节。只读核对表头、
文件长度及尾部索引得到：

| 案例 | 应有条目 | 文件实际条目等效数 | 最后一项 (band, Wannier, k) | 应有最后一项 |
|---|---:|---:|---|---|
| soc-0018 | 4,082,400 | 1,001,942 | (26,10,332) | (108,28,1350) |
| soc-0023 | 3,407,872 | 772,230 | (30,2,117) | (104,64,512) |

这两个 AMN 都明显截断，不满足运行外部 Wannier90 的前提。虽然 MMN/EIG 已有输出，
本轮没有为几 GB 的 MMN 做全量一致性认证，不能据“文件存在”就宣告矩阵已完成。
生成 .win 中 num_bands=128 与保留矩阵头不一致也需要处理，但改这个字段无法补齐
已经缺失的 AMN 条目。

因此不采用忽略 exit 255、只改 .win，或者复用半成品的“修复”。需要修正执行路径后
重新生成完整且来源一致的矩阵。原失败目录保持只读。

## 4. 验收

先分别验证实际带数记录正确、VASP 正常结束、所有矩阵记录完整、来源和编号映射一致，然后
运行独立 Wannier90 并检查 DIS 状态和同 k 比较。最后再跑 agent 全流程。

技术修复前后的科学方案、窗口、轨道、排除列表和目标应保持一致；如果科学角色主动
修改这些内容，则另立科学方案版本和审批，不能把它混入技术修复对照。
